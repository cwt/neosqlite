# NeoSQLite v1.15.1 Release Notes

## TL;DR

NeoSQLite v1.15.1 is a **focused correctness patch** fixing ten SQL-tier bugs (across five areas) surfaced while verifying v1.15.0 against real MongoDB. All fixes are backward compatible; no API changes.

**Key Fixes:**
1. **Expression converter parameter mismatches** — `$setEquals`, `$split`, `$dateFromString`, `$indexOfBytes`, `$strcasecmp`, `$cmp` no longer emit "Incorrect number of bindings supplied" and silently fall back.
2. **`$graphLookup` restrict clause** — `restrictSearchWithMatch` no longer fails with "ambiguous column name: data" inside the recursive JOIN.
3. **`$sortArray` numeric `sortBy`** — MongoDB-valid `sortBy: 1` / `-1` now sorts by element value in both SQL and Python tiers.
4. **Parameter binding order** — `$in`, `$regexFind`, `$regexFindAll` with literal operands no longer bind values to the wrong placeholders (previously returned silently wrong results).
5. **Real `_id` preservation** — tier-2 `$lookup` and `$graphLookup` no longer replace the primary key with the auto-increment id when `_id` differs from `id`.

- **Upgrade if you use:** aggregation pipelines with the affected expression operators, `$graphLookup` with `restrictSearchWithMatch`, `$lookup` on `_id`, or collections with non-auto-increment `_id` values.
- **Impact:** Better SQL-tier coverage and several silently wrong edge-case results corrected. No breaking API changes.

## Correctness Transparency Note

This section exists to prevent a false impression about the recent bug-fix volume. We want to be clear about how these bugs came to be and what users actually experienced:

1. **Most of the fixes in v1.15.0 were on-process bugs.** The deep audit's 86 findings were all remediated **within the v1.15.0 release cycle itself** — between the v1.14.15 tag and the v1.15.0 tag. No released version of NeoSQLite ever contained them: v1.14.15 users were never exposed, and v1.15.0 shipped with every fix already in place. A subset of these were introduced by that cycle's restructuring (for example, the tier-1 `$group` CTE-contract regression caused by the stage-builder split, and the translation-cache parameter divergence from the evaluator deduplication); the rest were pre-existing latent defects the audit surfaced. Either way, they were fixed **before release**.

2. **Most of the fixes in this release were shielded by the Tier-3 Python fallback.** Of the ten bugs fixed in v1.15.1, six were introduced during the v1.15.0 development cycle (the SQL converter expansion and query-builder changes) and one more pair (`$strcasecmp`/`$cmp`) predates v1.14.15. All of these failed **inside the SQL tiers**, were caught, and silently fell back to the authoritative Python tier — so results returned to users were correct at all times. The API comparison suite stayed at 0 failures throughout the entire cycle.

3. **Two fixes address edge shapes that were *not* shielded** and could return silently wrong results — both pre-existing since before v1.14.15, not v1.15.0 regressions:
   - `$in` / `$regexFind` / `$regexFindAll` with **literal** operands bound parameters in the wrong order (e.g., `{$in: [1, [1, 2, 3]]}` evaluated to `false`).
   - `$lookup` / `$graphLookup` on collections where the logical `_id` differs from the auto-increment `id` injected the wrong value as `$._id`.

In short: the fix counts in v1.15.0 and v1.15.1 reflect engineering velocity inside their own release cycles, not a history of shipping broken behavior.

## Overview

This release follows the v1.15.0 audit and expansion with a verification pass against real MongoDB, which surfaced five areas of SQL-tier defects. Six of the ten bugs were regressions introduced by the v1.15.0 refactoring and operator-expansion work; the other four were latent issues predating v1.14.15. All are fixed, regression-tested, and verified against MongoDB 8.0 with the API comparison suite (0 failures).

## SQL Tier Fixes

### Expression Converter Parameter Mismatches (#171)

**Affected operators:** `$setEquals`, `$split`, `$dateFromString`, `$indexOfBytes`, `$strcasecmp`, `$cmp`

Several converters reuse the same parameterized SQL fragment more than once (CASE branches, EXISTS arms, `instr()` null-guards) but appended its parameters only once. SQLite rejected the statement ("Incorrect number of bindings supplied"), the tier-2 processor aborted, and the pipeline silently fell back to the Python tier — correct results, wasted work, and warning noise.

The converters now duplicate parameters in the exact order the placeholders appear in the SQL, following the convention already established by `$replaceOne`.

- `$setEquals`: `array1, array2, array2, array1`
- `$indexOfBytes` / `$strcasecmp` / `$cmp`: repeated string/left-right fragment order
- `$split` / `$dateFromString`: duplicated for the null-guard and the main expression

### `$graphLookup` Restrict Clause Column Qualification (#172)

`restrictSearchWithMatch` is compiled against the target collection as a standalone `FROM` context, but the tier-2 implementation embeds it in a two-table JOIN where the target is only addressable as alias `t`. The unqualified `json_type(data, ...)` and `json_each(data, ...)` references emitted by the WHERE builder produced "ambiguous column name: data", and `_id` clauses referencing the quoted table name produced "no such column: employees._id" — both falling back to Python.

Every data-column function reference is now retargeted to `t.data`, and quoted-table `_id`/`id` references become `t._id`/`t.id`.

### `$sortArray` Numeric `sortBy` (#173)

MongoDB accepts `sortBy: 1` / `-1` to sort by element value. The SQL converter rejected the numeric form with a misleading `ValueError`, and the Python evaluator — the fallback tier — silently returned the array unsorted. Both tiers now sort by value, ascending for `1` and descending for `-1` (BSON comparison order in Python, value ordering in SQL).

The API comparison fixture now uses unsorted input arrays so this path is genuinely exercised against MongoDB.

### Parameter Binding Order: `$in`, `$regexFind`, `$regexFindAll` (#174)

These converters emitted placeholders in one order but bound parameters in another. When both operands were literals (both parameterized), Tier-1 executed with swapped semantics and returned silently wrong results — no fallback triggered:

- `{$in: [1, [1, 2, 3]]}` evaluated to `false` (the array was bound where the value belonged)
- `$regexFind` / `$regexFindAll` used the input string as the regex pattern, returning `NULL` / `[]`

Parameters now bind in SQL order (array before value for `$in`; pattern before input for the regex find operators).

### Real `_id` Through Tier-2 `$lookup` and `$graphLookup` (#175)

Both stages injected the auto-increment `id` column into the document JSON as `$._id`. Whenever the logical `_id` differed from `id`:

- outer documents came back with a corrupted primary key (e.g., `_id: 2` instead of `6`), and
- `$lookup` with `localField`/`foreignField` `_id` joined against the wrong value, returning empty arrays.

Both stages now preserve the `_id` column end-to-end (the `(id, _id, data)` invariant), `$lookup` joins `_id` on the dedicated column, `$graphLookup` carries `t._id` through the recursive CTE, and joined documents embed their real foreign `_id` — matching Tier-1 and MongoDB. (The Python fallback tier still strips `_id` from joined `$lookup` documents; that pre-existing divergence is tracked separately.)

## Migration Guide

### Upgrading from v1.15.0

No API changes and no intentional behavior changes. Two edge shapes now return **different (correct) results** where the SQL tier previously returned wrong values without falling back:

1. **Literal-operand `$in` / `$regexFind` / `$regexFindAll`**: these now evaluate with the correct operand order.
2. **`$lookup` / `$graphLookup` with `_id` ≠ `id`**: documents now keep their real `_id`, and `_id`-keyed joins return their matches.

Everything else is internal: pipelines that previously fell back to the Python tier may now stay in a faster SQL tier with identical results.
